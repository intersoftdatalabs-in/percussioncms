## Issue 2 — Jetty Starts With WARNINGS and ERRORS

**Severity:** 🛑 Multiple — see sub-issues.

### 2.1 — Jetty forks a second JVM for `perc-logging` and `perc` 🟡

```
WARN : Forking second JVM due to forking module(s): [perc-logging, perc]. Use --dry-run to generate the command line to avoid forking.
```

**Impact:** A second JVM is forked at startup to host `perc-logging` and `perc`. Each fork doubles memory use and slows startup; it also breaks log line ordering between the parent and child JVMs.
**Action:**
1. Run the start command with `--dry-run` to inspect the underlying command line and identify the fork boundary.
2. Remove the forking requirement for `perc-logging` and `perc` so they run in-process in the typical CMS install.

### 2.2 — SLF4J multiple providers → NOP logger fallback 🟡

```
SLF4J(W): Class path contains multiple SLF4J providers.
SLF4J(W): Found provider [org.apache.logging.slf4j.SLF4JServiceProvider@41a4555e]
SLF4J(W): Found provider [org.eclipse.jetty.logging.JettyLoggingServiceProvider@3830f1c0]
SLF4J(W): See https://www.slf4j.org/codes.html#multiple_bindings for an explanation.
SLF4J(I): Actual provider is of type [org.apache.logging.slf4j.SLF4JServiceProvider@41a4555e]
SLF4J(E): A service provider failed to instantiate:
org.slf4j.spi.SLF4JServiceProvider: org.apache.logging.slf4j.SLF4JServiceProvider not a subtype
SLF4J(E): A service provider failed to instantiate:
org.slf4j.spi.SLF4JServiceProvider: org.eclipse.jetty.logging.JettyLoggingServiceProvider not a subtype
SLF4J(W): No SLF4J providers were found.
SLF4J(W): Defaulting to no-operation (NOP) logger implementation
SLF4J(W): See https://www.slf4j.org/codes.html#noProviders for further details.
```

**Impact:** Application logging routed through SLF4J (including audit and security events) is silently dropped. Subsequent log lines from the application code are missing from the runtime log.
**Action:**
1. Pick a single SLF4J provider — recommend Log4j 2's `log4j-slf4j2-impl`, since it is already on the classpath.
2. Exclude Jetty's `jetty-slf4j-impl` (or vice versa) from the runtime classpath.
3. Verify by reproducing a known INFO-level event and confirming it appears in the log file.

### 2.3 — Deprecated Jetty `ShutdownMonitor` API in use 🟢

```
WARN [ShutdownMonitor] org.eclipse.jetty.server.ShutdownMonitor is deprecated,
      and has been replaced with org.eclipse.jetty.server.ShutdownService
```

**Impact:** Current Jetty 12.1.7 still tolerates this, but the API will be removed in a future Jetty release.
**Action:** Update the Jetty base configuration to use `ShutdownService` instead of `ShutdownMonitor`.

### 2.7 — Rhythmyx webapp fails Spring init: HTTP 503 Service Unavailable 🛑

```
WARN [WebAppContext] Failed startup of context oeje11w.WebAppContext@…{ROOT,/,b=[file:///D:/install-8.2/cms-8.2/jetty/base/webapps/Rhythmyx/, …]}{D:\install-8.2\cms-8.2\jetty\base/webapps/Rhythmyx}
org.springframework.beans.factory.UnsatisfiedDependencyException:
  Error creating bean with name 'relationshipSummaryService' defined in URL
    [jar:file:/D:/install-8.2/cms-8.2/jetty/base/webapps/Rhythmyx/WEB-INF/lib/sitemanage-8.2.0-SNAPSHOT.jar
     !/com/percussion/share/relationship/service/impl/PSRelationshipSummaryService.class]:
  Unsatisfied dependency expressed through constructor parameter 2:
    No qualifying bean of type 'com.percussion.share.dao.IPSRelationshipCataloger' available:
      expected single matching bean but found 2: contentItemDao, relationshipCataloger
Caused by: org.springframework.beans.factory.NoUniqueBeanDefinitionException:
  No qualifying bean of type 'com.percussion.share.dao.IPSRelationshipCataloger' available:
    expected single matching bean but found 2: contentItemDao, relationshipCataloger
```

Symptom observed from a browser probe:

```
HTTP ERROR 503 Service Unavailable
URI:    http://localhost:9992/
STATUS: 503
MESSAGE: Service Unavailable
```

**Impact:** 🛑 Blocking — Jetty binds on port `9992`, but every HTTP request to the Rhythmyx ROOT webapp returns **503 Service Unavailable** because the Spring `WebApplicationContext` for `ROOT` never finished initializing. The CM1 UI is unreachable.

**Cause:** `PSRelationshipSummaryService` (in `sitemanage-8.2.0-SNAPSHOT.jar`) declares a constructor parameter of type `IPSRelationshipCataloger`, and Spring finds **two** beans matching that type — `contentItemDao` and `relationshipCataloger` — instead of exactly one.

**Action:**
1. Add `@Primary` to the intended `relationshipCataloger` bean (or `@Qualifier` on the constructor parameter), OR remove/rename the duplicate `contentItemDao` bean so only one bean matches `IPSRelationshipCataloger`.
2. Inspect `sitemanage` for any recent change that introduced a second bean of that type (duplicate `@Component` / `@Service` / `@Repository` scan, or a stray `<bean>` declaration in a Spring config XML).
3. Re-deploy and confirm the Rhythmyx webapp starts cleanly; the HTTP probe should then return 200.
