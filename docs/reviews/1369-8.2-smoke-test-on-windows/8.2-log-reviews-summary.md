## 4. `CMS-8.2-Analysis.ods` — Runtime Analysis Workbook (post-install)

This workbook is **not** a build log — it captures the **actual state of the deployed 8.2 server** at runtime, including startup traces from Jetty and HTTP probes from a browser. It surfaces the highest-priority issues in this analysis.

### 4.1 — `rest` module Spring test failures

| Module | Errors |
|--------|--------|
| `rest` | Cascading `[ERROR] … » IllegalState ApplicationContext failure threshold (1) exceeded: skipping repeated attempt to load context for [MergedContextConfiguration… testClass = com.percussion.rest.MainTest, …]`, plus the same pattern for `MainTest.testUniqueJacksonBeans`, `ContentTypesTest.testContextLoaded`, `ContentTypesTest.testListContentTypes`, `ContentTypesTest.testUniqueJacksonBeans`, and other Spring-driven tests. |

**Severity:** 🟡 Test infrastructure / Spring context failure — *tests are being skipped*, not just failing.
**Cause:** Spring's `ApplicationContext failure threshold (1) exceeded` policy aborts further attempts to load a given `MergedContextConfiguration` after the first failure. The first underlying `ApplicationContext` load failure (the *real* error) is being masked by the cascade of "skipping repeated attempt" messages.
**Action:**
1. Run the `rest` module's tests with `--debug` or verbose Surefire output to capture the **first** root-cause Spring context load failure (likely a missing bean, misconfigured property, or bean-wiring ambiguity).
2. Confirm the same wiring problem doesn't also explain the `relationshipSummaryService` `NoUniqueBeanDefinitionException` observed at runtime (see 4.2). The two could share a root cause.
3. Fix the root cause; the threshold-skip messages will disappear automatically.

### 4.2 — Rhythmyx webapp fails to start: `UnsatisfiedDependencyException` on `relationshipSummaryService` 🛑

```
[WebAppContext] Failed startup of context oeje11w.WebAppContext@…{ROOT,/,b=[file:///D:/install-8.2/cms-8.2/jetty/base/webapps/Rhythmyx/…]}
org.springframework.beans.factory.UnsatisfiedDependencyException:
  Error creating bean with name 'relationshipSummaryService' defined in URL
    [jar:file:/D:/install-8.2/cms-8.2/jetty/base/webapps/Rhythmyx/WEB-INF/lib/sitemanage-8.2.0-SNAPSHOT.jar
     !/com/percussion/share/relationship/service/impl/PSRelationshipSummaryService.class]:
  Unsatisfied dependency expressed through constructor parameter 2:
    No qualifying bean of type 'com.percussion.share.dao.IPSRelationshipCataloger' available:
      expected single matching bean but found 2: contentItemDao,relationshipCataloger
Caused by: org.springframework.beans.factory.NoUniqueBeanDefinitionException:
  No qualifying bean of type 'com.percussion.share.dao.IPSRelationshipCataloger' available:
    expected single matching bean but found 2: contentItemDao,relationshipCataloger
```

**Severity:** 🛑 **Blocking** — the Rhythmyx ROOT webapp cannot start; the CM1 UI is unreachable.
**Cause:** Spring's `PSRelationshipSummaryService` (in `sitemanage-8.2.0-SNAPSHOT.jar`) declares a constructor parameter of type `IPSRelationshipCataloger`, and Spring found **two** beans matching that type — `contentItemDao` and `relationshipCataloger` — instead of exactly one.
**Impact:** Jetty starts its HTTP connector (`Started oejs.ServerConnector@…{HTTP/1.1}{0.0.0.0:9992}`), but every request to the Rhythmyx webapp returns **HTTP 503 Service Unavailable** (see 4.3) because the Spring `WebApplicationContext` for `ROOT` never finished initializing.
**Action:**
1. Add `@Primary` to the intended `relationshipCataloger` bean (or `@Qualifier` on the constructor parameter), OR remove/rename the duplicate `contentItemDao` bean so only one bean matches `IPSRelationshipCataloger`.
2. Inspect `sitemanage` for any recent change that introduced a second bean of that type (likely a duplicate `@Component` / `@Service` / `@Repository` scan, or a stray `<bean>` declaration in a Spring config XML).
3. Re-deploy and confirm `ROOT` webapp starts cleanly; the HTTP probe should then return 200.

### 4.4 — SLF4J provider conflict / fallback to NOP logger

```
SLF4J(W): Class path contains multiple SLF4J providers.
SLF4J(W): Found provider [org.apache.logging.slf4j.SLF4JServiceProvider@…]
SLF4J(W): Found provider [org.eclipse.jetty.logging.JettyLoggingServiceProvider@…]
SLF4J(I): Actual provider is of type [org.apache.logging.slf4j.SLF4JServiceProvider@…]
…
SLF4J(E): A service provider failed to instantiate:
  org.slf4j.spi.SLF4JServiceProvider:
    org.apache.logging.slf4j.SLF4JServiceProvider not a subtype
SLF4J(E): A service provider failed to instantiate:
  org.slf4j.spi.SLF4JServiceProvider:
    org.eclipse.jetty.logging.JettyLoggingServiceProvider not a subtype
SLF4J(W): No SLF4J providers were found.
SLF4J(W): Defaulting to no-operation (NOP) logger implementation
```

**Severity:** 🟡 Medium — actual application logging is silently **dropped** (NOP) until the conflict is resolved.
**Cause:** Both `log4j-slf4j2-impl` (Log4j 2's SLF4J provider) and Jetty's own `jetty-slf4j-impl` are on the runtime classpath. SLF4J can't pick one and falls back to NOP, so **app logs (and possibly audit/security events) are not being persisted** through SLF4J at runtime.
**Action:**
1. Decide on a single SLF4J provider (recommend Log4j 2's, since `log4j-slf4j2-impl` is already in use upstream).
2. Exclude Jetty's `jetty-slf4j-impl` (or vice versa) from the `sitemanage` war / Jetty base classpath.
3. Confirm app logs are no longer NOP by reproducing a known INFO-level event and checking the log file.
